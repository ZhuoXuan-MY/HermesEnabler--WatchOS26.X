# GestaltX v1.1.1 — 设备配对与路径获取源码核验 / Device Pairing and Path Discovery Audit

> **研究范围：** 我的第一代 Apple Watch Ultra，`Watch6,18 / n199ap`，watchOS **26.6.1**（`23U95`）。  
> **核验日期：** 2026-11-14（北京时间 / Asia/Kuala_Lumpur，UTC+08）。  
> **外部版本：** [huamidev/GestaltX v1.1.1](https://github.com/huamidev/GestaltX/releases/tag/v1.1.1)，build **`11140102`**；官方发布于 **2026-11-14 00:46:05（UTC+08）**（GitHub published_at: 2026-11-13 16:46:05 UTC）。  
> **方法和限制：** 我通过 GitHub 读取该版本的发布说明、README、Swift 和 Rust 源码进行静态核查。**未安装 GestaltX、未连接或配对我的 Apple Watch、未在 Xcode 编译运行，也没有执行权限穿透或修改 MobileGestalt 文件。** 本报告不把公开源码分析冒充 `23U95` 真机结果。

## 我为什么关注这次更新

我原先的阻碍不只是找到 MobileGestalt 缓存路径：在 **真实 Ultra 1 / `23U95`** 上，我已能读取部分受保护缓存，但尝试 `open(O_RDWR)` 返回 **`EPERM`**；取得并激活 Class 13 sandbox extension 不意味着有文件写入权限。此外，Hermès2025 与 Circulaire/Poodle 还存在独立的原生表盘资格、枚举和添加限制。

因此我检查 GestaltX 1.1.1 新增的 **“Pairing & Device Connection: used to obtain required paths”** 到底指哪台设备、怎样连接、拿到的是什么路径，以及是否改变上述阻碍。

## 逐项源码核验

| 检查项 | 我实际找到的证据 | 对 `Watch6,18 / 23U95` 的影响 |
|---|---|---|
| **官方发布范围** | [v1.1.1 release](https://github.com/huamidev/GestaltX/releases/tag/v1.1.1) 新增 App Audio Library（通知声音替换、路径采集引导）和 Pairing & Device Connection，并修复侧载版配对问题、重装后配对文件路径迁移问题 | 更新属实，但发行说明**未宣称支持 watchOS 或赋予系统写入权限** |
| **项目明确支持的平台** | [README.md（v1.1.1）](https://github.com/huamidev/GestaltX/blob/v1.1.1/README.md) 说明面向 **iPhone/iPad**，支持 **iOS/iPadOS 27.x** 的本机 MobileGestalt 访问；明确称 iOS 26.x **不支持**这项本机访问，SystemGroup 依赖 iOS 27 | 官方支持承诺**不覆盖 Apple Watch / watchOS 26.6.1** |
| **“配对”的目标** | [`DeviceConnectionView.swift`](https://github.com/huamidev/GestaltX/blob/v1.1.1/GestaltX/DeviceConnectionView.swift) 显示 **“Pair this iPhone once”**；引导在 iPhone **Privacy & Security → Developer Mode** 中进行本机配对 | 我确认该 UI 是 **iPhone 自配对**，不是通过 iPhone 向配对的 Apple Watch 请求系统文件权限 |
| **通信实现** | [`DeviceConnectionModel.swift`](https://github.com/huamidev/GestaltX/blob/v1.1.1/GestaltX/DeviceConnectionModel.swift) 启动 pairing host 并保存 pairing record；[Rust `device/mod.rs`](https://github.com/huamidev/GestaltX/blob/v1.1.1/Native/DeviceConsole/src/device/mod.rs) 通过远程配对、RSD/Lockdown 和 LocalDevVPN 回环通道连接。代码注释明确 **“connection path only, no Airlift exploit”** | 这是一种**配对后访问允许的诊断服务**的架构；本身不是 watchOS 越狱、sandbox escape 或任意受保护路径的读写授权 |
| **路径的实际用途** | [`NotificationSoundCaptureModel.swift`](https://github.com/huamidev/GestaltX/blob/v1.1.1/GestaltX/NotificationSoundCaptureModel.swift) 调用 `runSyslog`；Rust 后端连接 **`com.apple.syslog_relay`**；日志解析器提取通知声音文件路径 | 可以为**可访问的 iPhone 日志/应用音频文件**提供路径线索；取得路径**不等于**取得该路径的读取或写入权限 |
| **是否直接支持 Watch 的系统 MG** | 上述 1.1.1 pairing、console、notification-sound 模块中**未发现**目标 Apple Watch 的配对/连接入口、`23U95` 系统缓存写入代码或 Watch SystemGroup 授权分支 | **没有证据**可以通过本次新增功能绕过真实 Ultra 1 的 `open(O_RDWR) → EPERM` |
| **构建是否总能启用 console** | [`DeviceConsole.swift`](https://github.com/huamidev/GestaltX/blob/v1.1.1/GestaltX/DeviceConsole.swift) 和 [INTEGRATION.md](https://github.com/huamidev/GestaltX/blob/v1.1.1/Native/DeviceConsole/INTEGRATION.md) 显示需要原生 `GXDeviceConsole` 框架与编译条件 **`GXDEVICECONSOLE`**；不满足时直接报告控制台不可用 | 我核对的是**源码能力**，不能据此声称每个第三方重签 IPA 都已正确启用连接或采集 |

**本次最重要的区分：** “设备配对成功” ≠ “可以访问配对的 Apple Watch” ≠ “知道文件路径” ≠ “获得 Apple Watch 受保护 SystemGroup 的写入权限”。

## 与既有研究的关系

我在此前 [Filza / Gestalt 工具审查](2026-11-12-watchOS26-Filza-Gestalt-Security-Audit.md)、[WorstGestalt / WatchRegion 独立源码验证](2026-11-12-WorstGestalt-WatchRegion-Static-Validation.md) 和 [RO23 状态记录](RO23-STATUS.zh-CN.md) 中分别确认了不同边界：

- **Filza、GestaltX 的 iPhone 文件路径或连接信息**，不能自动修改配对手表的受保护缓存。
- **WorstGestalt 的 `bad_query` 文件级 Class 13 变体**仍是另外一条待验证研究线索；GestaltX 1.1.1 的配对组件**没有提供已验证的同类 watchOS 权限结果**。
- **WatchRegion** 有 watchOS 27 的公开实机报告，不能直接推断在 `23U95` 可工作。
- **即使将来解决系统缓存写入**，仍必须独立验证 Hermès 表盘的设备资格、正常添加流程与重启后的持久显示。

## 下一步是否值得借鉴

**可以参考的只有诊断架构**：远程配对、RSD/Lockdown 通道、诊断服务、只读日志与可复核的来源标记。如果今后出现确实面向 Apple Watch 的已授权诊断服务或可验证的手表端采集证据，才值得重新评估。不能把当前 iPhone 的 self-pairing 代码直接当成 Watch 访问通道。

本轮我**不合并 GestaltX 代码、不修改本项目 `HermesEnabler2` Swift/Objective-C 程序、不写系统缓存、不安装 IPA、不启动新的强制解锁版本**。仅把这个外部更新和源码证据记录到项目历史。

**结论：有辅助分析价值，但不是新的 `Watch6,18 / 23U95` 漏洞、路径穿透、`EPERM` 修复或原生 Hermès 表盘解锁。项目状态仍为 `BLOCKED / NOT UNLOCKED`。**

## English summary — verified source review, not a Watch unlock

On November 14, 2026 (UTC+08), I reviewed [GestaltX v1.1.1](https://github.com/huamidev/GestaltX/releases/tag/v1.1.1), build `11140102`, against my target **first-generation Apple Watch Ultra (Watch6,18), watchOS 26.6.1 (23U95)**.

The release introduces **Pairing & Device Connection** to support path discovery for its new **App Audio Library**, plus fixes for side-loaded pairing and moved pairing-file paths. The version-tagged source explicitly says **“Pair this iPhone once”** and implements **iPhone self-pairing** with RSD/Lockdown, a loopback VPN, and `syslog_relay` capture. The native Rust source labels this **a connection path, not an Airlift exploit**. Console availability also depends on the `GXDEVICECONSOLE` build integration.

The official README supports **iPhone/iPad iOS/iPadOS 27.x** for direct MobileGestalt access and explicitly excludes iOS/iPadOS 26.x for this capability. I found **no evidence of a Watch6,18/23U95 system-cache write, watchOS sandbox escape, or successful native Hermès activation** in the inspected 1.1.1 components. Discovering an iPhone notification-sound path does not grant write access to a paired Watch's protected SystemGroup.

**Evidence level: upstream release + static source review only**. No Xcode build, IPA installation, pairing with my Watch, physical-device test, protected write, or unlock occurred. My project remains **BLOCKED**. Historical records and code remain unchanged; this report is documentation-only.
